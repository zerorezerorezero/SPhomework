# 程式實作說明

## 一、銀行存提款模擬 (`bank.py`)

### 目的
模擬同一個銀行帳戶同時進行多次存款和提款，演示 Race Condition 的發生以及使用 Mutex 解決問題。

### 實作方式
- 使用兩個執行緒：一個負責存款 100,000 次（每次 +1），另一個負責提款 100,000 次（每次 -1）
- **實驗 1 — 不加鎖**：直接對共享變數 `bank_balance` 進行操作，由於 `balance += 1` 在 CPU 層級並非原子操作（需要：讀取 → 計算 → 寫入），多執行緒交錯執行會導致 Race Condition，最終餘額不為 0
- **實驗 2 — 加 Mutex**：使用 `threading.Lock()` 包住每次存取操作，保證同一時間只有一個執行緒能修改餘額，結果必定正確

### 執行結果
```
[實驗 1] 不使用 Mutex
實際最終餘額: -2794  (每次執行結果不同)
=> 發生 Race Condition！結果不正確！

[實驗 2] 使用 Mutex
實際最終餘額: 0
=> 正確！Mutex 保證了資料一致性！
```

## 二、生產者消費者問題 (`producer_consumer.py`)

### 目的
模擬經典的生產者-消費者問題，使用執行緒同步來協調生產與消費。

### 實作方式
- 使用 `queue.Queue` 作為有限緩衝區（大小為 5），Queue 內部自帶 Mutex 和 Condition 變數，自動處理同步
- 2 個生產者執行緒：每次生產一個商品放入佇列，若佇列滿則自動阻塞
- 2 個消費者執行緒：每次從佇列取出一個商品消費，若佇列空則自動阻塞
- 透過 `produced_lock` 確保生產計數器的原子操作
- 使用 `q.join()` 等待所有商品被消費完畢

### 流程
```
生產者 → 放入 Queue → 消費者
         (緩衝區)
```
- 當 Queue 滿時，生產者自動等待
- 當 Queue 空時，消費者自動等待
- 透過 Queue 的內部鎖機制保證了執行緒安全

## 三、哲學家用餐問題 (`dining_philosophers.py`)

### 目的
模擬經典的哲學家用餐問題，展示 Deadlock 的發生條件以及解決方法。

### 問題描述
5 位哲學家圍坐圓桌，每兩位之間有一支叉子。哲學家需要同時拿起左右兩支叉子才能用餐。如果所有哲學家同時拿起左邊的叉子，就會形成 Deadlock。

### 實作方式
使用「左撇子解法」破壞循環等待條件：
- 第 0 位哲學家先拿右叉再拿左叉（與其他人相反）
- 其他 4 位哲學家先拿左叉再拿右叉
- 這樣就不會形成循環等待，從而避免 Deadlock

### 為什麼左撇子解法有效？
原本的等待鏈：P0→右叉→P1右叉(=P0左叉), P1→左叉→P2左叉(=P1右叉), ...
```
原本循環：P0(左) → P1(左) → P2(左) → P3(左) → P4(左) → P0(左)
                                       ↓
左撇子解法：P0(右) → P1(左) → P2(左) → P3(左) → P4(左)  ↛  P0(左)  (循環中斷！)
```
由於 P0 先拿右叉（也就是 P1 的左叉），P1 拿左叉時可能被 P0 卡住，破壞了原本的循環等待。
